## 一、总体目标

**一句话**：让插件的**状态文件（名册）**在**多个 DSH 进程同时写**时**永远不会被写坏**。

**为什么这是最高优先级**：2026-10-13 上午真实发生了一次 —— 两名协调者同时报「团队名册丢了」，
根因是**两个进程同时写同一个临时文件**，把 `.dsh/team-link/policy.json` 写出了 73 字节的撕裂
（完整部分 834,315 字节仍可解析，尾部多了垃圾 ⇒ **整份读不出来**）。

**影响面**：名册、68 组配对、12 个看门狗注册**全部读不出来** ⇒ 插件退回「仅进程内存」状态 ⇒
所有会话看到的名册都是空的。**这次是运气**（坏在尾部、完整部分可救）；坏在中间就**不可恢复**。

## 二、问题（现象 + 根因，带 file:line 证据）

### 2.1 现象（真机实测，2026-10-13）

| 项 | 读数 |
| --- | --- |
| 文件 | `C:\Users\huangchaowen\.dsh\team-link\policy.json` |
| 总长度（**单位必须写明**） | **841,978 字节 = 834,388 字符**（差 7,590 是中文等多字节字符造成） |
| 其中**完整可解析部分** | **841,905 字节 = 834,315 字符**（`JSON.parse` 通过，10 个团队） |
| 尾部垃圾 | **73 字节 = 73 字符**（纯 ASCII，两边同值） |
| 解析结果 | `Unexpected non-whitespace character after JSON at position 834322`（**字符**位置） |
| 实际内容 | 一个**完整正确的 JSON 文档** ＋ 一段**重复的文档尾部**（`"resources": true } } }` ×2） |
| 现场备份 | `policy.json.corrupt-2026-10-13T02-36-07-303Z`（父侧原样留存） |

**撕裂的精确形态（以**字符**计 —— 写入者交错发生在字符域）**：`834,388 − 834,315 = 73`
—— 即「甲进程写完的 **834,315** 个字符」之上，**乙进程从字符偏移 834,315 起写了 73 个字符**。
这是**同一 inode 上两个写者交错**的典型签名。

> ★ **本节的口径更正（设计评审 🟡#7 的处置，2026-10-13）**：原文把**字节**与**字符**混着用
> （表格写 `841,978`、撕裂段却用 `834,388 − 834,315`，两个数在**不同单位**下才都成立），
> 读者无法自洽。现在**每一处都写明单位**，权威读数由上表四行给出（可用
> `policy.json.corrupt-…` 那份备份**重新实测复现**）。根因结论不受影响。

### 2.2 根因（`lib/index.js:1895-1906`，逐行）

```js
async function writePolicyFileAtomic(file, text) {
    await mkdir(path.dirname(file), { recursive: true });
    const tmp = `${file}.tmp`;          // ← ① 临时文件名写死：所有写入者共用同一个
    const handle = await open(tmp, "w"); // ← ② "w" 截断：乙打开时把甲**正在写**的文件清零
    try {
        await handle.writeFile(text, "utf8");
        await handle.sync();
    } finally {
        await handle.close();
    }
    await rename(tmp, file);             // ← ③ 谁先 rename 谁赢；另一个随后 rename 同一路径
}
```

**三条缺陷叠加**（每一条单独都不致命，合起来就撕裂）：

1. **`tmp` 名字固定**（`:1897`）—— 两个进程落在**同一个** `<file>.tmp` 上；
2. **`open(tmp, "w")` 会截断**（`:1898`）—— 乙进程的 `open` 把甲的临时文件清零，
   于是两个 `writeFile` 在**同一 inode 的不同期望长度**上交错；
3. **`rename` 无重试**（`:1905`）—— Windows 上目标被占用时 `rename` 会抛错，
   调用方（`policy.update` 的各个写点）**没有重试**，失败方向不明。

**为什么现在才炸**：这份文件已涨到 **814 KB**（10 团队 + 68 配对 + 12 看门狗）。
**写得越久，两个进程的时间窗重叠概率越大** —— 这正是「文件长大了才开始坏」的原因。

### 2.3 事实核对（排除其他嫌疑人）

| 嫌疑 | 核对结果 |
| --- | --- |
| 是不是「删团队」把名册删了？ | ❌ **不是**：完整部分含**全部 10 个团队**，无一条被删 |
| 是不是父侧（本会话）改坏的？ | ❌ **不是**：本会话 2026-10-11 起只改过「屏蔽」与「删团队」两块，**无一碰过这份文件的写法**（`git log -- lib/index.js` 逐条核对） |
| 有没有别的写入者绕过原子写？ | ❌ **没有**：全仓检索 `writeFileSync` / `createWriteStream` → **零命中**；`appendFile` 只写黑板（`decisions` / `tasks`），不碰 `policy.json`；`writeFile(file, …)` 的三处分别是 roster 镜像（`:5644`）、discipline（`:6943`）、handoff 文档（`:11633`）⇒ **`policy.json` 只有 `writePolicyFileAtomic` 一条写路径** |

⇒ **真凶唯一**：`writePolicyFileAtomic` 的共享临时文件名。

## 三、功能用户故事

| # | 用户故事 |
| --- | --- |
| **US-L1** | 作为**同时开着多个团队的维护者**，我要**同时有多个会话在写名册**时文件**依然完好**，这样我不会某天早上发现所有团队都「丢了」。 |
| **US-L2** | 作为**协调者会话**，当名册文件**已经损坏**时，我要在**读面**看到**如实的落点与原因**（`⚠ 存储：仅进程内存（重启即失）—— 原因：文件损坏（不覆盖；请人工处理）`），而不是看到「团队列表为空」这种**误导性**的空态。 |
| **US-L3** | 作为**排障的人**，当写盘失败时，我要在**日志与工具返回**里看到**点名到写入者的原因** —— 口径为「**落点文件路径 + 错误码（errno）+ 写入者函数名**」（★ 用户 2026-10-13 裁定，取代原写的 `file:line`：行号会随代码变动漂移，本仓文档纪律本就禁止拿行号当定位），而不是静默失败。 |

## 四、非功能标准

| # | 标准 |
| --- | --- |
| **NF-L1 零新依赖** | 顶层 `import` 仍**恰 8 条**（本批用的是既有 `open` / `rename` / `mkdir` / `path` / `os`）。既有两道锁（`批 H · NF-H5` / `批 I · U17`）保持不变。 |
| **NF-L2 原子性不降级** | 仍必须是「临时文件 → 写 → fsync → rename」；**不得**退化成「直接覆盖目标」（那会在崩溃窗口留下半写文件）。 |
| **NF-L3 可核** | 修复后必须有一条**真能红的**判据证明「并发写不再撕裂」：**去掉修复 ⇒ 该判据必红**。 |
| **NF-L4 失败方向 fail-closed** | 写盘失败**不得**静默成功：要么重试，要么如实报错；**不得**让调用方以为写成功了。 |
| **NF-L5 旧文件兼容** | 已损坏的文件**不自动覆盖**（沿用 §七 既有纪律：人工处置是唯一出口）。本批**不引入自动修复**（那会掩盖问题）。 |

---

## 五、明确的非目标（本批不做）

1. **不做自动修复**：读到损坏文件时**不**自动截断/重建（那会掩盖真实故障，且可能丢数据）。
2. **不改状态落点**：仍是 `settings` 在场走 settings、不在场走文件（`AGENTS.md` §七）；**不改成双写**。
3. **不引入文件锁 / 跨进程协调**（`flock`-类）：那要新依赖且跨平台行为不一 —— 本批用**唯一临时名**消除冲突即可。
4. **不改各写点的语义**（谁在什么时候写、写什么），只改**写入的实现**。
5. **不处理黑板的 `appendFile`**：黑板的追加写是另一条路径，本次事故与它无关。
