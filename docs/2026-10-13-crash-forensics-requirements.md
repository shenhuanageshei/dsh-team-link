## 一、总体目标

**一句话**：让 DSH **意外死掉的那一刻**留下一份**可读的现场**（内存、磁盘、当时在跑什么），
而不是像今天这样 —— 只知道「它死了」，**其余全空白**。

**为什么这事现在能做**：DSH 自己已有半个仪表（`~/.dsh/death-forensics/` 下的 `crash.log` / `heartbeat.log` / `state.json`），
但它**只记「什么时候停的」**（心跳只有 `ts` / `boot` / `pid` 三格）——
**没有任何一格能回答「死的时候机器什么样」**。本批补的是**这一格**。

**真机动机（2026-10-13 实测）**：崩溃史 **40 条**（`non-graceful-end`，自 2026-09-29 起），
最近两次死亡窗口：`2026-10-12T12:58:36Z → 2026-10-13T01:37:59Z` 与
`2026-10-13T00:18:52Z → 2026-10-13T01:37:59Z`（后者的**最后心跳停在 00:18:52**，
而进程当时已经死了 ⇒ **79 分钟的空白无人知道**）。

★ **设计输入出处（评审 🟡#2 要求留痕）**：本批**没有会诊** —— 输入 = **用户 2026-10-13 的直接裁定**
（父侧问「心跳跑在插件里还是独立进程」⇒ 用户答「**心跳装插件里**」）＋ 同日父侧对崩溃史的取证读数。

## 二、问题（现象 + 根因，带 file:line 证据）

### 2.1 现象：崩溃**零现场**

| 面 | 现状 | 结论 |
| --- | --- | --- |
| DSH 自带 `crash.log` | **只留最后 40 条**环形记录，每条只有 `kind` / `at` / `prevBoot` / `prevStartedAt` | 只知道「死了、什么时候」 |
| DSH 自带 `heartbeat.log` | 每行只有 `ts` / `boot` / `pid` **三格** | **没有内存 / 磁盘 / 负载** |
| DSH 自带 `state.json` | 只有 `bootId` / `pid` / `startedAt` / `lastEnd` | 同上 |
| 外部启动器日志 | 报告逐字写「**未找到** —— 非便携部署或未启用 `dsh-web-launch.ps1` 启动器」 | 无 |
| Windows 事件日志 | 近 24h 过滤 `dsh` / `electron` / `node` 的 Error/Critical = **空** | 无 |
| minidump / WER | **不存在** | 无 |

⇒ **崩溃现场 = 零**。这是本批要改变的唯一一件事。

### 2.2 根因（为什么现在是零）

**不是「没人想做」，是「没有东西在写」**：
1. DSH 自带的那半个仪表**只写三格**（时间 / 启动号 / 进程号 —— 见上表现状）；
2. 本插件**没有写任何崩溃相关的东西**（全仓检索：`death-forensics` **零命中**）；
3. 崩溃是**非正常退出**（`non-graceful-end`）⇒ **进程没有机会在退出时跑任何收尾代码**
   ⇒ 唯一可能留下现场的形态是「**在活着的时候持续写**」（心跳式），
   而不是「在死的时候写」（那种写永远不会发生）。

## 三、功能用户故事

| # | 用户故事 |
| --- | --- |
| **US-K1** | 作为**维护者**，当 DSH **突然死掉**时，我要在**下一次启动**就看清「它死之前那一刻：内存多少、磁盘余量多少、有几个会话活着、几个看门狗在跑」，这样我不用再靠猜。 |
| **US-K2** | 作为**维护者**，我要**一眼看出「死与上一次心跳之间有多久没人知道」**（今天的 79 分钟空白就是这一格），这样才能判断它是「当场崩」还是「崩了之后一直躺着」。 |
| **US-K3** | 作为**维护者**，我要这份现场**随时可读**（一条工具命令），**不必去翻文件、不必懂内部结构**。 |
| **US-K4** | 作为**维护者**，我要它在**正常运行时不打扰我**：不刷屏、不发通知、不占满磁盘（有上限）。 |

## 四、非功能标准

| # | 标准 |
| --- | --- |
| **NF-K1 零新依赖** | 顶层 `import` 仍**恰 8 条**（需要 `statfs` 时只在既有 `node:fs/promises` 那一行的**解构列表**里加名字 —— **条数与说明符不变**，与批 L 同一手法，两批若同批实施须在报告里点名）。 |
| **NF-K2 写不坏自己的状态** | 心跳写在**它自己的目录**里，**绝不碰** `policy.json` / 黑板 / DSH 自带的 `death-forensics`（那是宿主的地盘，且它写着我们读不到的内部结构）。 |
| **NF-K3 有界** | 心跳目录**按启动次数**保留上限（默认 **10** 次启动），超出按最旧清理；单个文件是**定长小 JSON**（远小于 1 KB）。 |
| **NF-K4 失败静默** | 心跳**写失败不许影响任何功能**（failing 只允许在日志里留一行，绝不抛进热路径）—— 它是**观测**，不是功能。 |
| **NF-K5 可核** | 判据必须能**真红**：把「写心跳」那一步去掉 ⇒ 判据红；把「保留上限」去掉 ⇒ 上限判据红。 |

## 五、明确的非目标（本批不做）

1. **不做崩溃归因**：本批**只留现场、不解释原因**（解释要等有了几组现场才谈）。
2. **不接管宿主的地盘**：不写、不改、不删 `~/.dsh/death-forensics/` 下的任何文件，**并且本批一概不读它** ——
   死亡窗口**完全由插件自家心跳推导**（`lastBeatAt` → 本次 `startedAt`）。★ 本行口径由设计评审 🟡#2 更正：
   原文写「只**读**它来算死亡窗口」，与设计档 FR-K3「纯用自家心跳」矛盾；**以本行为准**（不读宿主任何文件）。
3. **不做外部收集器**：不发 HTTP、不起独立进程（`node:http` 不在白名单里，且「外部证人」是更重的一步 —— 见设计档 §4 D6）。
4. **不记录会话内容**：只记**计数**与**资源读数**，不记任何消息文本（那是另一个隐私面）。
5. **不读宿主作业服务**：插件**读不到**宿主的在飞作业清单（本批实测：模块级 `inject` 只有 4 项，无 `jobs`）
   ⇒ 「在飞作业数」**本批不做**，如实登记为已知缺口（**不许**用猜测的数字冒充）。
