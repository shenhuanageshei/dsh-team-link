# 策略持久化自持化（设计 · 2026-09-27）

> **一句话**：让「团队 / 策略」的落点**可核** —— `settings` 服务可用时优先用它；不可用时落到**插件自己的文件**；两者都不行才退回进程内存，且**每一次成功的写入都必须能在磁盘上指出落点**。

---

## §1 现象与证据（2026-09-27 真机诊断，desktop 部署）

| # | 读数 | 含义 |
|---|---|---|
| 1 | 建队那一刻，`<DSH_HOME>` 下**没有任何设置文件被写**（只有别的插件的 store） | 写路径没落到磁盘 |

## §2 需求与判据（R）

- **R1 持久**：settings 不可用的部署里，团队/策略**重启后仍在**。
- **R2 可核（红线）**：任何写入都必须能指出落点（服务 / 文件 / 仅内存）；**「仅内存」必须显式可见**，不许静默。
- **R3 不回归**：settings 可用的部署里行为与今天一致（仍走服务，且**不**新建文件）。
- **R4 迁移**：把孤儿数据（`cordis.patch.yml` 的 `teams`）一次性导入新落点。
- **R5 原子**：崩溃/断电不得产生半个状态文件。

---

## §3 设计

### 3.1 落点优先级（三档 → 四档）

1. **settings 已 attach** ⇒ 用它（与今天一致，`scope` 非空）。
2. **未 attach、但能写文件** ⇒ **文件后端** `<DSH_HOME>/team-link/policy.json`。
3. **文件也不可写** ⇒ 进程内存 + 恰好一行 warn（**现状**，保留为最后兜底）。
4. **文件有数据、服务后来 attach** ⇒ **折叠**：把文件内容并进服务，服务成为落点；并列痕。

> 复用现有机制：插件本就有「**memory-only startup window** → 服务晚挂时折叠」的完整逻辑（`memoryDirty` / 折叠 warn / 失败保留重试）。本设计把那个「memory」从**纯内存**换成**文件支撑**，是同一套逻辑的对称扩展，不是新发明。

### 3.2 路径解析（新增，插件目前完全不读环境）

- `DSH_HOME`（实测存在：`C:\Users\magic\.dsh`）⇒ 目录 `<DSH_HOME>/team-link/`，文件 `policy.json`。
- 缺失时退回 `os.homedir()/.dsh/team-link/policy.json`；两者都拿不到 ⇒ 落第 3 档 + warn。
- **落在全局目录，不落工作区**：团队是按名字全局寻址的（只有会话列表是工作区作用域），放工作区会造成「换个工作区团队就没了」。

### 3.3 写入语义

- **原子**：写 `<file>.tmp` → `fsync` → `rename` 覆盖目标；目录先 `mkdir -p`。
- **写失败**：保留内存态 + warn（**不静默**），下一次写入重试。
- **只写一处**：attach 成功后**不再写文件**（避免双写不一致）；反之亦然。

### 3.4 可核（R2 的落地面）

`team_link_roster action=get` 与 `team_link_status` 的**首行**显示当前落点，三态各一句：

- `存储：设置服务（team-link 命名空间）`
- `存储：文件 <绝对路径>`
- `⚠ 存储：仅进程内存（重启即失）—— 原因：<not-active | no-register | 文件不可写>`

### 3.5 迁移（R4）

- 代码侧**不读宿主配置文件**（那是不该有的耦合）。
- 一次性数据迁移由实做者/父侧**手工执行一次**：把 `cordis.patch.yml` 里 `team-link.config.teams` 的内容写成新 `policy.json`，并在账本留读数（迁移前后各一条）。
- 既有的 legacy 命名空间迁移（`session-link-pro` → `team-link`）**一行不动**。

## §4 判据（断言清单，实施前必须逐条先红）

| 号 | 断言 | 档 |
|---|---|---|
| U1 | 无服务时：写 → 读回一致，且文件存在 | 文件后端 |
| U2 | 原子：留下半写 `.tmp` 不影响读取（读只认 `policy.json`） | 原子 |
| U3 | 折叠：文件有数据 + 服务后 attach ⇒ 数据并入服务，随后落点是服务 | 折叠 |
| U4 | 冲突：文件与服务都有数据 ⇒ 更晚修改者胜 + 留痕（不静默覆盖） | 折叠 |

| U6 | 回归：服务可用时**不**创建/不写文件 | 红线 R3 |
| U7 | 路径：`DSH_HOME` 缺失 → 退回 homedir；两者皆缺 → 内存 + warn | 路径 |
| U8 | 回归：legacy 命名空间迁移行为不变 | 迁移 |

## §7 明确不做（避免过度设计）

- ✗ **不双写**（服务与文件各写一份）—— 不一致的代价高于收益。
- ✗ **不读宿主配置文件**（`cordis.patch.yml`）—— 迁移一次性手工做，代码不耦合宿主内部结构。
- ✗ **不改宿主 / 不改 profile 加载方式** —— 本设计只动插件自身。
- ⚠ **残留风险**：文件与服务长期分歧时以「更晚修改者胜」处理并留痕；若用户希望更强一致性（例如服务侧为准），那是另一个设计题。
