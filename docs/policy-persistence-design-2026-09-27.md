## §3 设计

### 3.1 落点优先级（三档 → 四档 → 五档）

1. **settings 已 attach** ⇒ 用它（与今天一致，`scope` 非空）。
2. **未 attach、但能写文件** ⇒ **文件后端** `<DSH_HOME>/team-link/policy.json`。
3. **文件也不可写** ⇒ 进程内存 + 恰好一行 warn（**现状**，保留为最后兜底）。
4. **文件有数据、服务后来 attach** ⇒ **折叠**：把文件内容并进服务，服务成为落点；并列痕。**折叠落定后立即把「合并结果」重写回文件并盖 `foldedAt`**（实为 attach 后置链**末端**，理由见 verification-log）—— 这样若服务之后再次缺席（重启回第 2 档），文件里是**合并后的真值**，不会是折叠前的过期快照（否则折叠后新建的团队会表现为「消失」）。
5. **快路径折叠（分歧审计修复轮 🟡#5 增补，2026-09-27）**：服务在 activation 就已 attach 时同样走第 4 档，**不再因为「挂得早」而不读文件**。
   - 服务**为默认** + 文件**有状态** ⇒ **折叠**（并入服务 + 留痕 + 合并结果回写文件并盖 `foldedAt`），规则与第 4 档**同一条**；
   - 服务**非默认** ⇒ 按 3.3 **服务胜**，文件那一侧**连读都不读**（U6 第二条断言：零字节变动）。

   > 增补理由：原实现里 `loadPolicyFile()` 只有一个调用点（`if (scope === null)`），于是「服务从一开始就在场」的部署**永远读不到文件** —— 文件后端时期写下的团队在下次启动里不可见，正是 §1 现象的形状，而 U6 的第二条断言把它锁成了规格。

> 复用现有机制：插件本就有「**memory-only startup window** → 服务晚挂时折叠」的完整逻辑（`memoryDirty` / 折叠 warn / 失败保留重试）。本设计把那个「memory」从**纯内存**换成**文件支撑**，是同一套逻辑的对称扩展，不是新发明。

### 3.2 路径解析（新增，插件目前完全不读环境）

- `DSH_HOME`（实测存在：`C:\Users\magic\.dsh`）⇒ 目录 `<DSH_HOME>/team-link/`，文件 `policy.json`。
- 缺失时退回 `os.homedir()/.dsh/team-link/policy.json`；两者都拿不到 ⇒ 落第 3 档 + warn。
- **落在全局目录，不落工作区**：团队是按名字全局寻址的（只有会话列表是工作区作用域），放工作区会造成「换个工作区团队就没了」。

### 3.3 文件 schema（评审 🟡#1 补）

```json
{ "schema": 1, "savedAt": "2026-09-27T06:26:24.786Z", "foldedAt": null, "policy": { /* 与 settings 命名空间同键集 */ } }
```

- `policy` 的键集**镜像** settings 命名空间（迁移时不得有损，迁移型改动必须一次性写全）。
- `savedAt`：每次成功写入刷新（出处）；`foldedAt`：折叠落定时刻（`null` = 从未折叠）。
- **折叠胜负裁决不靠时间戳**（服务侧没有可比时间），沿用本仓既有的 legacy 迁移规则：**服务非默认 ⇒ 服务胜（文件归档 `policy.superseded-<ts>.json` 并留痕）；服务为默认而文件非默认 ⇒ 文件折叠进服务；两边都非默认 ⇒ 服务胜 + 留痕**（不做静默合并）。

### 3.4 写入语义

- **原子**：写 `<file>.tmp` → `fsync` → `rename` 覆盖目标；目录先 `mkdir -p`。
- **写失败**：保留内存态 + warn（**不静默**），下一次写入重试。warn 门**按段复位**（代码评审修复轮 🟡#2）：一道门 `fileWriteWarned` 过去是**进程级一次性**的，于是第一段失败 warn 过之后，再下一次失败完全静默；现在**写入成功即复位** ⇒ 一段失败 = 一行，成功后新的一段失败再报一行（与 `attachWarned` 按窗口复位同一范式）。
- **损坏档守卫（代码评审修复轮 🟡#1 新增）**：载入时判定文件**损坏**（读不出 / 非法 JSON / 没有 `policy` 对象 —— **`policy` 是数组也算**：数组不是命名空间镜像，会被 `normalizePolicy` 读成一份全默认的空视图；代码评审第 2 轮 🔵#2 补上，判据即 `typeof doc.policy !== "object" || Array.isArray(doc.policy)`，与「缺失 / null」走同一条置坏分支）之后，**一律不覆盖**那份文件 —— 每一次写都直接返回并在留痕里**如实说明**（不静默，也不吞掉第二次以后）。修复前这里只有一个「本次不会覆盖该文件」的 warn 而 `persistPolicyFile` **毫无守卫**，于是文件后端下**下一次任何写入**都会用原子 rename 把损坏文件整个替换掉，落点行还会从「⚠ 仅进程内存」翻成「存储：文件」（`policyPlacement` 只看 `fileUsable`）。
  - **人工处置 = 唯一出口**：`policy.json` 损坏时插件**不猜、不合并、不覆盖**，只把状态落进程内存并报第 5 个原因码；**修好或移走该文件**（用户自己动手）后重启进程即恢复。每个 store 只读一次文件，所以「修好了但插件还在跑」不会自动生效。
- **只写一处**：attach 成功后**不再写文件**（避免双写不一致）；反之亦然。**读**不受这条约束 —— 读只发生在「服务为默认」这一支（§3.1 第 5 档），写仍然只有一处。
- **`foldedAt` 只由折叠落定（代码评审修复轮 🔵#3 新增）**：回写合并结果时**只有本次链上确有折叠/裁决落定**才盖新戳，判据取折叠那一步的结局（`MEMORY_WINDOW_OUTCOME_NONE` = 「未挂载期间无写入」那一种除外；**catch 支例外**：链在折叠结果产出**之前**断掉时读不到那个结局，catch 那一支对 `syncFileFromService` 显式传 `foldHappened: false` —— **宁可漏盖不冒盖**，保留上一次真正落定的戳，代码评审第 2 轮 🟡#1）。修复前无条件盖戳，于是「最近一次 attach 时刻」冒充「折叠落定时刻」；**回写本身不受这条约束**（U3/U4/U8/U10 要求的合并结果写回照旧），只是没有折叠的那一段保留上一次真正落定的戳，逐字节不动。
- **`fold failed` 不回写（代码评审第 3 轮 🟡#1 新增）**：折叠**失败**（`fold failed` —— 窗口数据没并入服务、仍只活在文件里）的那一次，链尾**连回写都不做**：把服务视图写回文件会把窗口数据从内存与文件**两边同时**抹掉（内存这边在回写里被服务视图整份替换），且不留归档。文件保留未并入的那一份，与折叠失败那一行留痕（「仍在落点里、本次未能并入」）逐字一致；`memoryDirty` 保持置位，下一次 attach 的折叠会重试。盖戳判据同批收紧为「**确已落定**的两个结局」（`folded into settings` / `not folded`）才为真 —— `fold failed` 对旧判据（`outcome !== NONE`）取真，照样盖新戳，与「宁可漏盖不冒盖」相反。**不用「先归档再覆盖」那条路**：归档救不回内存那份镜像，宁可保守不回写。

### 3.5 可核（R2 的落地面）

`team_link_roster action=get` 与 `team_link_status` 的**首行**显示当前落点，三态各一句：

- `存储：设置服务（team-link 命名空间）`
- `存储：文件 <绝对路径>`
- `⚠ 存储：仅进程内存（重启即失）—— 原因：<not-active | no-register | 路径解析失败 | 文件不可写 | 文件损坏（不覆盖；请人工处理）>`
  - 前四个里 `路径解析失败` 与 `文件不可写` 同源，都是「拿不到可写的落点」；
  - **第 5 项 `文件损坏（不覆盖；请人工处理）` 是代码评审修复轮 🟡#1 增补的**，与既有四项并列。它与「不可写」**不是**同一件事：文件**写得进去**，插件只是**拒绝**用它（§3.4 的损坏档守卫），并把「人工处置」这条唯一出口写在原因码里。
  - **两因并存时并陈（代码评审第 2 轮 🔵#3）**：服务侧 `no-register` 与文件侧原因（`路径解析失败` / `文件不可写` / `文件损坏`）**同时**成立时，落点行**并陈**两条 —— `⚠ 存储：仅进程内存（重启即失）—— 原因：no-register；另：文件损坏（不覆盖；请人工处理）`。**优先序**：主因仍取 `no-register`（与服务侧单因形态一致），文件侧那一因以 `；另：` 附在后面；**四种单因形态逐字不变**（只有一条原因时不出现「另：」）。修复前 `no-register` 独占一行，把「文件损坏、请人工处理」这条唯一行动信号整个吞掉。

### 3.6 迁移（R4）

- **迁移前置（分歧审计修复轮 🟡#5 增补）**：手工导入 `policy.json` 之前，先确认那一份**真的会被读到** —— 服务侧的 settings 命名空间此刻必须是空的（服务非默认时按 §3.3 服务胜，文件那一份**连读都不读**）。服务里已经有团队时，先导出、比对、再决定是「直接用服务侧」还是「先把服务侧清空再导入」；否则导入的文件会安静地躺在磁盘上不生效（正是本次修复前快路径的形状）。
- 代码侧**不读宿主配置文件**（那是不该有的耦合）。
- 一次性数据迁移由实做者/父侧**手工执行一次**：把 `cordis.patch.yml` 里 `team-link.config.teams` 的内容写成新 `policy.json`，并在账本留读数（迁移前后各一条）。
- 既有的 legacy 命名空间迁移（`session-link-pro` → `team-link`）**一行不动**。

## §7 明确不做（避免过度设计）

- ✗ **不双写**（服务与文件各写一份）—— 不一致的代价高于收益。
- ✗ **不读宿主配置文件**（`cordis.patch.yml`）—— 迁移一次性手工做，代码不耦合宿主内部结构。
- ✗ **不改宿主 / 不改 profile 加载方式** —— 本设计只动插件自身。
- ⚠ **残留风险 1**：文件与服务分歧按 3.3 的裁决规则处理并留痕（**不做静默合并**）；若用户要更强一致性，那是另一个设计题。
- ⚠ **残留风险 2（评审 🟡#3）**：`policy.json` 是**全局单文件**，而本插件跨进程 —— **两个 DSH 进程同时写同一文件无锁、可能丢更新**。本设计**不做文件锁**（代价大于收益），如实声明；缓解 = 原子写 + 每次写入都是「读-改-写整份」，冲突窗口很小，且折叠/迁移路径均有留痕。
- ⚠ **残留风险 3（分歧审计修复轮 🟡#5）**：快路径折叠的前提是「attach 那一刻读到的命名空间还是默认的」。若某个更早的钩子（第三方插件、配置 HMR）已经往命名空间里写过东西，本插件会按 §3.3 判**服务胜**，文件那一份不读也不并 —— 这是**裁定如此**，不是漏读：那一支的可核出口是**折叠裁决 / 归档 / 留痕三件套**，一行不少。真要迁移过去，走 §3.6 的一次性手工导入（并先满足那里的前置条件）。
