## 一、总体目标

让团队能**从名册里真正删掉** —— 包括**已经退役**（没有现任协调者）的那些；**磁盘上的黑板文件不动**。

今天只有 `retire`：它把 `current` 置空（vacant），**名册行仍在**、版本史仍在。于是一个不再需要的团队**永远留在团队列表里**，
只能走设置 UI 手工改 `teams` 键（而那条路 `AGENTS.md` §七 明确说「不会生效」—— 本部署的状态事实源是 `policy.json`）。

**一句话**：现在能「停用」团队，不能「清掉」团队；再加上一个。

## 二、功能用户故事

| # | 故事 | 今天的行为（痛点） |
| --- | --- | --- |
| **US-H1** | 作为用户，我要把不再需要的团队**从名册里清掉** | `retire` 之后名册行还在 ⇒ 团队列表里**永远留着**，越积越多 |
| **US-H2** | 作为用户，我要能删**已退役**（没有现任协调者）的队 | 若只允许「现任协调者」发起，**已退役的队谁都删不掉** —— 而它们恰恰是最该清的（真机两例：`u9-verify-1012` / `u9b-verify-1012`，都是我为验证建的临时队，用毕退役后卡在名册里） |
| **US-H3** | 作为用户，删之前我要看到**删的是哪个队**，并且有机会取消 | 删名册行不可逆（版本史一并消失）⇒ 需要一次显式确认 |
| **US-H4** | 作为用户，我删掉的**只是名册**，团队的**台账与交接文档要原样留着** | 若连黑板一起删，真实团队的决策史就没了（真机反例：`2026-10-08` 的 tasks.md 有 64 行真实台账） |

## 三、非功能标准

| # | 标准 | 判据方向 |
| --- | --- | --- |
| **NF-H1** | **不误伤**：删的**只有** `teams` 里那一行（连同它自己的 `history`）；`policy` 的其它字段（`watchdogs` / `pairs` / `trustedSenders` / `rememberTargets` / 其它团队）**一个字节不动**，除非按既有 `retire` 的同一路径清理指向该队的信任 | 盘上 diff 逐字段比对 |
| **NF-H2** | **不碰黑板文件**：`<workspace>/team/<队名>/` 下的**文件内容**不读不写不删（★ 评审 🔵#5 限定：**目录级存在性探测**一次是允许的唯读操作 —— 否则 FR-H4③「目录不存在也如实说」做不到；除这一次探测外，目录**内容**一概不读） | 删除前后目录（含每个文件的字节与 mtime）逐字节相同 |
| **NF-H3** | **幂等 / 如实拒绝**：删一个不存在的队 ⇒ **拒绝并列出已知团队名**（不是静默成功） | 可红的负相判据 |
| **NF-H4** | **可机械验证**：判据必须能红（删前后名册行数 / `history` 在场性 / 其它字段逐字节不变） | 红相夹具 + 负相自证 |
| **NF-H5** | **零新依赖**：不得新增 import（`host-half.test.mjs` 的八模块白名单是硬闸门） | 静态扫描 `^import` 仍 8 条 |
| **NF-H6** | **不做双写**：状态落点仍单写 `policy.update`（`AGENTS.md` §七） | 落点行三态不变 |

## 四、明确的非目标（本批不做）

1. **不删黑板文件**（已拍板）—— 删完如实报出目录路径，让人自己决定要不要手工清；
2. **不做归档**（把黑板打包到别处再删）—— 要另立项；
3. **不做批量删**（一次删多个队）—— 一次一个，确认框也一次一个；
4. **不改 `retire` 的既有语义**（它仍是「停用」，不删行）；
5. **不动 `policy.writer` / 权限模型**的**判定逻辑** —— 具体说：`delete` **动作本身豁免** writer gate（依据 §五 ②「谁都能发起删」；否则 US-H2 的核心场景 —— 已退役、无现任协调者的队 —— **谁都删不掉**），把关改由**人类确认框**承担；**其它动作的 gate 逐字不变**（设计档 §8-U8 钉住）。
   ★ 评审 🟡#1 更正：原写「删的发起权与既有工具的 writer gate **同规**」，与本档 US-H2 / §五 ②、以及设计档 D2 的「豁免 gate」**正面冲突** —— 已按用户裁定改准。
