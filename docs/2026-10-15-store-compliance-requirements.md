## 一、总体目标

**一句话**：让这个插件**通过 DSH STORE 的上架自动审查**（当前被判 `catalog-blocked`），**而不改变任何一项对外行为**。

**为什么做**：商城收录 = 下游用户**能装、能找到**；现在卡在**打包形态**（单文件过大）与**声明缺失**（Node 范围、依赖/权限说明），**不是**功能或安全问题（商城原文：**不是安全漏洞指控，也不表示项目质量有问题**）。

**★ 本批的红线（先写死）**：**这是一次纯形态/声明改动** —— 对外行为、工具面、判据**一条都不许变**；唯一的例外是本仓自设的「顶层 import 恰 8 条」闸门，它必须**同批改写**成新口径（因拆分必然引入内部相对导入）。

## 二、问题（现象 + 根因，带 file/字节证据）

| 商城判定 | 我们的实况（当次实测） | 根因 |
| --- | --- | --- |
| **最大单文件超限**（上限 **262,144 B**） | `lib/index.js` = **1,092,693 B**（越限 **4.17 倍**）；`lib/client.js` = 156,665 B（合规） | 全部宿主半边实现集中在一个文件里（长期单文件演进的结果） |
| **未声明 Node 兼容范围** | `package.json` **无 `engines` 字段** | 从来没有显式声明过 |
| **运行时依赖需单独供应链审查** | 运行时依赖**恰 1 个**：`schemastery@^3.0.0` | 声明面缺失（不是依赖本身有问题） |
| **固定源扫描不完整** / **未观察的能力信号未知** | 无独立证据 | **推测**是「单文件超限 ⇒ 扫描做不完」的连带结果（**待修完第一条后由商城复检判定**，本档不猜死） |

## 三、功能用户故事

| # | 用户故事 |
| --- | --- |
| **US-R1** | 作为**下游用户**，我要能在 DSH STORE 里**装到这个插件**（而不是看到 `catalog-blocked`）。 |
| **US-R2** | 作为**审查方/下游**，我要能从仓库里**一眼读到**这个插件的依赖、权限、外部服务与失败边界（不必读一万行源码）。 |
| **US-R3** | 作为**下游用户**，我要看到它**诚实声明的运行范围**（Node / DSH 版本），而不是一个我们不保证的宽区间。 |
| **US-R4** | 作为**维护者**，我要有**一份可复现的「装 / 启 / 卸」证据**，证明它在**干净 profile** 里也能装得上、起得来、卸得干净。 |
| **US-R5（★ 红线）** | 作为**现有用户**，**这次改动对我的使用体验零影响**：工具面、参数、行为、判据**逐字不变**。 |

## 五、明确的非目标（本批不做）

1. **不改任何对外行为**（工具面、参数、返回文案、判据语义）。
2. **不改 `lib/client.js`**（156,665 B 已合规）—— 除非拆分导致它必须跟着改导入路径。
3. **不引入构建/打包工具**（tsup / esbuild / rollup 一律不上）。
4. **不新增依赖**（含 devDependencies）。
5. **不追求商城的其它未提出项**（如额外的审计报告、签名）。
6. **不改宿主兼容区间**（`peerDependencies` 保持现状；换代复核是既有的独立纪律）。
7. **不删 `docs/` 出 `files`**（文档是用户面的一部分；商城那条限的是**单文件运行源**，不是文档）。
