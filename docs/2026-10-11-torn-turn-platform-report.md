# 观测报告（给 DSH / 宿主侧）· 崩溃打断回合后，恢复出来的历史**永久不合法**（会话作废）

> 2026-10-11 · 由 dsh-team-link 维护侧起草 · **本报告不改本仓任何东西**，只陈述观测与建议。
> 触发场景：用户报告 `dsh://session/team-link-mal-analyze-1011-worker-2-ec485211` 出现 `tool_use` 失败。

## 一、一句话

**DSH 在一次 OOM 崩溃中打断了一个正在执行的回合；重启恢复之后，该会话组装给 provider 的历史里
有一个 `tool_use` 找不到配对的 `tool_result` ⇒ provider 拒绝请求 ⇒ 此后**每一回合**都以同一个错误失败（会话作废）。**

## 二、证据（可复核）

### 2.1 失败读数（逐字）

```
turn=7  2026-10-11 04:26:00  kind=interrupted          ← OOM 的死亡窗口（最后心跳 04:25:56，重启 04:27:52）
turn=8  2026-10-11 04:38:29  kind=error
        messages.39.2: `tool_use` ids were found without `tool_result` blocks immediately after:
        call_4fd3d31d23a34be190c30edc. Each `tool_use` block must have a corresponding
        `tool_result` block in the next message.
turn=9  2026-10-11 04:39:10  kind=error   （用户发了「继续」，同样的错）
```

### 2.2 被点名的那个调用

| 项 | 读数 |
| --- | --- |
| 工具 | **`pwsh`**（**不是** team-link 的任何工具） |
| 发出 | `seq 450`，2026-10-10 18:06:19，turn 3 step 47 |
| **结果** | **`seq 451`，2026-10-10 18:06:22 —— 结果在日志里，长度 288** |

⇒ **不是「结果没落库」**。日志里配对是好的；断的是**组装成 provider 消息数组**那一步。

### 2.3 为什么判定与崩溃/恢复有关（而不是历史里本来就有问题）

| 时刻 | 事件 | 说明 |
| --- | --- | --- |
| 18:06:19 / 18:06:22 | `call_4fd3d…` 与其结果 | **配对完整** |
| 18:07:19 → 20:25:33 | turn 3 收尾 + turn 4 / 5 / 6 全部 `kind=completed` | ⇒ **这几轮都成功发过请求** ⇒ 那时组装出来的是合法历史 |
| **04:25:47** | turn 7 开始（`agent/inbox/spliced` 投递一条用户消息） | |
| **04:26:00** | **turn 7 `kind=interrupted`** | ★ **OOM 死亡窗口内** |
| 04:38:27 | turn 8 开始（重启后 25 分钟） | |
| 04:38:29 / 04:39:10 | turn 8 / 9 双双 `kind=error` | ★ **此后每一回合都失败** |

⇒ 中间只发生了一件事：**崩溃 + 重启恢复**。日志侧没有任何新写入去破坏那一对。

### 2.4 排除项

- **不是 team-link 插件**：被点名的调用是宿主自带的 `pwsh`；插件在本会话里只贡献了它一贯的
  段 / 资源行 / 工具回执文本，没有任何「改写他人回合消息」的能力（它**没有**会话日志写入面 ——
  本仓有一条既有判据把宿主模块的导入面钉成八个已审计模块，专门防止它长出写入 API）。
- **不是压缩/剪枝**：`compaction/prune` 的 7 次都发生在 17:51–18:04（**远早于**），且每次
  `shadowedRange` 都是**整条消息**（`start === end`，如 `{21,21}`、`{423,423}`），不是半条；
  压缩后 turn 3–6 仍正常完成。
- **不是工具本身失败**：`pwsh` 那次返回正常（288 字节读数）。

## 三、机制推断（供宿主侧定位）

错误里的 `messages.39.2` 是**组装后数组**的坐标（第 39 条消息的第 2 个 block），
它**不对应日志里的任何一条 seq** —— 说明断点在 **resume 路径的组装逻辑**里，最可能是：

1. 恢复时对「被中断的回合」的收尾不足（该回合里未闭合的 `tool_use` 没有被补一条结果或整个丢弃）；**或**
2. 组装器在压缩摘要 + 恢复点交界处，把某个 `tool_result` 归到了非相邻位置（provider 的规则是
   「**immediately after**」—— 中间插进任何别的消息都会违例）。

两种都可以用一条本地复现：**制造一次「工具调用在飞时杀进程」，重启后发一条消息**，看是否复现同一错误。

## 四、建议

| # | 建议 | 为什么 | 难度 |
| --- | --- | --- | --- |
| **1** | **恢复时修复「被中断的回合」**：对未闭合的 `tool_use` 补一条合成的 `tool_result`（内容如「本次调用被进程中断，未返回结果」），或把该回合整体丢弃 | 这是根因；补一条就能让会话继续可用 | 中等 |
| **2** | **把这类错误标成不可重试并提供出口**：GUI 提示「该会话历史已损坏，继续重试不会成功；请新建会话（团队席位可用 `reappoint` 换人）」 | 用户现在看到的只是一条红；实际是**重试永远失败**，会白烧很多轮 | 低 |
| **3** | **加一条自检**：恢复时对组装结果跑一次「每个 `tool_use` 后面紧跟其 `tool_result`」的不变量检查，失败就**当场修复或明确报错** | 把这类损坏挡在「消耗用户回合」之前 | 低 |
| **4** | 崩溃原因本身：本仓只观测到 `non-graceful-end`（OOM），修复不在本报告范围 | — | — |

## 五、给用户的即时处置（本仓口径）

- **别重试**：turn 8 / 9 已经证明重试是同一个错；每次重试只是再浪费一个回合。
- **可靠恢复 = 新会话**（旧会话的日志已在盘上，不丢证据）。
- **如果损坏的是团队席位**：本插件给了团队级出口 ——
  `team_link_recover action=reappoint`（**人改任**：由人类在对话框里挑一个候选，
  插件建新会话、铸一次性令牌、把待迁移信任与交接正文投给继任者）。这正是「窄恢复路径」的用途。
