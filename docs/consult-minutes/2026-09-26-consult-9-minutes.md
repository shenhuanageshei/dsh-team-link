## 总立场：先立一条原则，再谈机制

用户担心的「涌现的自主核对」来自**信息不对称**：每个会话只有自己的私有上下文，想对齐就必须重述、反问、互查。任何被全队共享的可变状态，都会**消灭核对的理由**——板子说什么，大家就信什么。所以四问共用一条设计原则：

> **共享状态是「主张」，不是「事实」。板子记录的是「谁在何时声称了什么」，永远不溶解成「团队的状态」。**

不信任应该同样指向板子本身。

## Q1 任务板 + 队列映射：两层结构，映射做成「读时视图」而非新存储

- **不要**抄内置的 CAS 可变行（"latest wins = truth"）。用你们已有的 `decisions.md` 形态：**append-only、带署名的主张流**是原始层；「当前状态」是**派生投影**（每个键取最新主张），并显式标注「派生、可从原始层重建、不可单独采信」。这和你们 verdict 体系的哲学同构：日志是事实，verdict 是一次读。
- **可反驳做成一等状态**：任何成员可对某键追加一条「存疑/与我观测不符」的主张；投影遇矛盾显示 `conflicted`，**绝不按时间戳或 revision 自动裁决**——裁对决路径是两个会话之间发消息，板子只记录裁决结果这条新主张。
- **队列→任务的映射不要建物理队列**（新增持久状态、排序与恢复问题、和 fail-closed 投递相冲）。消息信封已有 `meta.ref`（≤16 字符，`lib/index.js:3229` 起）——把「ref 携带任务键」固化成约定，然后做一个**只读的按任务分组收件视图**，从会话日志现算。队列是日志上的一个视图，不是新存储。
- **状态永不由投递事件自动推进**（"送达即完成"这种自动化 = 未经核对的真理）。只有成员的显式主张能推进状态。

## Q2 持久投递队列：不采纳，写成「有意识的分道」

内置邮箱解决的是**藏起未投递**；你们的「未投递即退出、❌ 首行、发送方善后」恰恰是不信任体系的一部分：没送到，发送方当场知道、当场重判。持久队列会把「对方从没看见」悄悄变成「以后会看见」，这有两个毒性：(a) 排队消息可能在换届/吊销**之后**送达——信任决策是针对一个已经过去的时刻做的；(b) 又是一处「会误判的持久状态」（你们的看门狗去抖特意用进程内 Map，README:480）。折中：**发送方自己的重试**是发送方的私事（插件可以让重发更顺手，比如返回体里带重发骨架），但插件不持有任何跨会话代发队列。

## Q3 形态切换：指针不拷贝、人不点头不切、拒绝时刺眼

- 名册**必须分区**，且比「分两张表」更严：`agent-team` 模式下 `teams` 键里只存一个**指针**（Lead 会话/TeamId），成员视图读时现算、标注「来源：宿主 Agent Teams」，**一行都不拷贝**进 settings——同一事实两个来源就是用户担心的那种混乱。
- 切换是信任敏感操作（投递面变了）：走与换届同级的**人授权卡点**，切换本身在 `decisions.md` 记一条（模式史可审计）；消息**不跨形态改投**——A 形态下发的消息永不因切到 B 而重路由，桥接由模型自己做。
- 宿主没开 Agent Teams 时**大声拒绝**并点名缺失能力，绝不降级到多会话形态。对宿主团队**只读不写**：不代理 spawn/派活——既避开实验 API 的 schema 变更风险，也不在两套权限模型之间发明第三套。

## Q4 主会话上下文治理：现在不加机制，加「锚 + 信封纪律 + 派生视图」

三个失败形态从未发生，机制先行就是过度工程。真正护住主管会话的和护住对等会话的是同一件事：**带署名的冗余，而不是更少信息**。危险从来不是体量，是：无署名的合并摘要（N 份回报混成一个声音 = 没人可怀疑）、压缩后目标失锚、插队混乱。对应三件便宜事：

1. **锚，不过滤**：把换届交接文档契约（§11.9.6 那个形态）泛化成「当前任务书」——协调者把任务书写进团队目录，每条派发指令引用它。压缩吃掉目标后一次读就复原。这是会**显性出错**的文档（人随时可读），不是会暗地误判的隐藏状态。
2. **信封纪律**：`type/pri/ref` 已存在（`lib/index.js:3225–3296`），在 `discipline.md` 里加一条约定：并发任务 >N 时，P2 回报用「主张 + 证据指针」而非全文倾倒。这是纪律条款，不是代码。
3. **多路回报的合并只发生在模型自己的回合里**（一次 turn 读完 k 条、产出**逐来源署名**的裁决摘要），插件层**绝不**做消息拦截/合并——插件一合并，来源的声音就没了，用户要的互核也就没了。若真要机制，只考虑「协调者侧成批排干的纪律」，仍不是代码。
4. **回执（M5 积压项）换一种实现**：不做新持久账本。插件本来就在读会话日志（verdict 就是这么来的），做一个**纯派生的只读视图**：「已投递但目标日志无后续反应」，零新增状态，完全合你们哲学。注意依赖：这类日志派生视图先要解 `PREVIEW_SESSIONS = 12`（`lib/index.js:116`），该 P1 是前置。

## 守护涌现的三条硬规则 + 一个反面预警

1. **署名强制**：板上每行必须指名主张者（与 decisions.md 同构）。
2. **矛盾一等**：投影显示冲突，永不自动裁决。

4. 反面失败也要盯：板子太权威时，会话会**停止说话、只写行**——团队安静、互核死亡。前导指标可测：消息量塌缩而板子写入增长。这可以是只读面板上的一条诊断注记，同样不是机制。

# 会诊意见：Q1–Q4（关于任务板、持久队列、形态切换、上下文治理）

## 零、先回答用户最在意的那个元问题：涌现的自主核对会不会被杀死

**已核实的关键事实**：消息信封上已经有 `meta.ref` 字段（≤16 字符，lib/index.js:3278-3284），黑板 `decisions.md` 已经是「只追加 + 每行带作者会话 id + seq 由插件单调分配」的形状（lib/index.js:2558、2539-2541），`discipline.md` 是整文件替换 + baseHash 乐观锁。**也就是说：用户想要的「任务板 + 消息映射」，八成用现有件就能拼出来，不需要新机制。**

**我的核心判断（这是整份意见的纲）**：

> 涌现的自主核对，来源不是「全推」本身，而是三条：① 平级关系里没有权威可以甩锅；② 每个会话有独立的工具手，能自己去验货；③ 关于「现实」的声明（我做完了 / 测试过了）是以原话到达的，中间没有过一道别人的摘要。
>
> 所以安全的分界线是：**「账」可以搬出上下文（谁在干什么、派了什么活），「事」必须留在上下文里（关于现实的声明、以及对声明的核对）**。搬错任何一边才会杀死涌现：把声明搬到板子上，会话就会偷懒信板子；把账留在上下文，主会话才会被淹。

用户担心「共享状态变成唯一事实源、一个错误全员继承、没人核对」——这个担心**非常对**，而且它正是内置那套任务板（CAS 改状态）的本体论缺陷：板上写着 `done`，它就是「现实」。**解法不是不做板，而是让板在结构上无法成为事实源**——见 Q1。

## Q1：任务板 + 多消息队列映射 —— 赞成做，但形状必须是「台账」而不是「看板」

**反对**直接抄内置的 CAS 任务板（`team_task_*`：owner、revision、状态改写）。理由两条：

1. **信任模型不兼容**。内置的板子能 CAS，是因为所有写入者都是 Lead 的孩子，权限继承、天然可信。你们这边是平级不信任的会话：谁有资格把「T3 状态」从 doing 改成 done？CAS 语义在「谁都不替谁担保」的世界里没有仲裁者。
2. **它正是用户怕的那个东西**。状态可改写 ⇒ 板子自认为是现实 ⇒ 错误被全员继承 ⇒ 没人再核对。

**赞成**的形状：**任务台账 = `decisions.md` 的同构兄弟**（新增第三个黑板文件，比如 `tasks.md`）：

| 性质 | 怎么来的 | 效果 |
|---|---|---|
| 只追加 | 复用 decisions 的写入路径，seq 插件分配、单调递增 | 并发写不冲突，**根本不需要 CAS** |
| 每行带作者 | 现成的 `author-session-id` 列 | 板上只有「**A 声称** T3 完成 @10:22」，永远没有「T3 完成」 |
| 各行其道 | 约定：只有 owner 追加自己任务的状态行 | 没人能替别人记功/记过 |
| **可反驳原生** | 非 owner 用同一条写入路径追加一行「存疑：T3 与我观测不符（依据…）」 | 反驳不需要特殊机制，**和记账是同一个动作**；争议是新增行，不是改状态 |
| 可从消息重建 | 台账只是索引，消息流才是原始记录 | 板子坏了可以重放重建 —— 符合「不留会误判的持久状态」：派生索引错了不危险，因为它**不是真相，只是路标** |

**「多消息队列映射」**：不需要真的造队列数据结构。消息流本来就是多路的，缺的只是一个**归档键** —— 而 `meta.ref` 已经在那儿了。约定：派活时分配 `t-<seq>`，回报消息带 `ref=t-<seq>`。每条回报自己落进对应台账行。**这一步是纯约定，零代码。**

边际机制量：一个新文件枚举值 + 读取时按行过滤。其他全是约定。这是我能找到的最小解。

## Q2：持久投递队列 —— 明确反对现在做

现状（已核实）：未投递即退出、内容不保留、发送方善后；且代码里有一条明文纪律「失败永远不能被读成已排队」（lib/index.js:3487 附近的注释原则）。

三条反对理由，一条比一条硬：

1. **它偷偷改变了授权求值的时机**。现在的双门批准发生在「发送这一刻」。队列意味着「批准在此刻、投递在彼刻」——中间如果配对被吊销、换届发生，队列里的消息还算不算数？要正确处理就得**在排空时重新过一遍双门**，等于把信任逻辑复制一份，这正是你们最警惕的新信任面。
2. **它和可见性纪律打架**。你们刚在 0.3.x 立了「结果必须可见，成功失败都要」（设计档 §10.2.8.10）。队列的本质是「投递结果在时间上不透明」——消息进了队，发送方看到什么？「已排队」恰恰是你们明令禁止的读法。
3. **它解决的问题目前不存在**。目标不在线的场景，现有组合（发送方善后 + 看门狗 tick + 黑板留言）已经兜住。为一个没发生过的场景引入一块**最难做对的持久状态**，不值。

**将来真要翻案的前置条件**（写进纪要，免得以后重新吵）：有人真的需要「定时夜班交接给不在线的会话」；且排空时重过双门的方案过评审；且队列内容对发送方全程可查可撤。三条缺一，维持现状。

## Q3：形态切换（人定、可来回切）—— 三条硬规矩

用户已定：只能人切，但不定死。我的意见是切换**可以做**，但要按换届的既有机器做，不要新造：

1. **名册必须分区，永不合并**。两个来源的名册（插件 settings 的 `teams` 键 vs Lead 会话日志）各有各的主人，合并成一张表就是「一个真相两个写手」——Q1 的同一个陷阱。`agent-team` 形态下插件只读、不拥有，输出里老实标「来源：宿主」。
2. **不悄悄降级**。形态 = `agent-team` 而宿主没开 Agent Teams ⇒ 硬错误、亮出来、fail-closed。和你们「宁可不发，不默认放行」（README:235）是同一条纪律，别在这儿破例。
3. **切换 = 换届进另一个底座**。复用现有的交接机器：退役旧团队记录 → 建新记录 → **黑板文件整体随迁**（decisions/discipline/tasks 都是底座无关的，这是它们作为文件的天然优势）。**信任对不自动回迁**：从 agent-team 切回多会话时，旧 pairs 可能已过期，必须人重新点批准 —— 还是 fail-closed。

切换动作本身走人类确认门（和你们其他授权点同形），模型可以提议、不能执行。

## Q4：主会话并发回报 + 人持续输入 —— 风险评估与三件约定级手段

**先给风险评估**（直接回答「我现在该不该慌」）：不该慌，但该铺轨。三个理由：

- 用户实测：三种症状（回报太长 / 输入被打断 / 压缩吃掉目标）**长期未出现** —— 当前规模在阈值之下；
- 结构上有一层天然保护（已核实）：消息是在**步边界**注入运行中会话的（lib/index.js:3753），每条回报大致各得其所，不会在半句话里插队；
- 但有一个**真实的、随规模放大的洞**：派活的原始计划目前只活在主会话的上下文里。DSH 压缩不知道哪段是「原始计划」。N 变大 + 会话变长之后，「压缩吃掉目标」是三种症状里**最先咬人**的那个。

**三件手段，全是约定级，不碰投递、不合并、不摘要**：

1. **派活即落账**（治「压缩吃掉目标」）：协调员派活时在 tasks 台账追加一行（带 `t-<seq>`）。计划从此住在文件里，压缩够不着。主会话失忆后 `team_link_team_read` 一次读回 —— 这个工具已经存在，返回 roster + 黑板，今天就能这么用。
2. **回报必带 ref**（治「回报太多理不清」）：`meta.ref=t-<seq>`。主会话收到回报不需要记得全部计划，看到 ref 就知道是哪件事；上下文里每条回报从「一团内容」变成「某个已知任务的更新」。`meta.ref` 字段今天已经存在、已经过校验、已经渲染在 banner 里。
3. **协调员纪律写进 `discipline.md`**（治「输入打断+注意力散」）：这个文件就是干这个的，今天已经存在。写四条白话规矩：回报按 ref 归档、先归档后行动、验货去查文件不查板子、记不清就读板子不靠回忆。零代码。

**明确不做**（这比做什么更重要）：

- **不做自动合并/摘要多条回报**。合并器就是一个摘要层，摘要层的错误会被全员继承 —— 这是 Q1 陷阱的再现，而且会直接杀死涌现核对（会话核对的是原话，不是二手摘要）。主战历史上提过「合并投递」的建议，我**反对**那条，理由在此。
