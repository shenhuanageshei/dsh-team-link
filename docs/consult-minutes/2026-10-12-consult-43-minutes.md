## ② 与既有到期清扫 / rearm / stopTimer 打不打架

**不打架，但插入位置是硬约束。**逐条核过：

- **顺序**：续期必须是 `patrolOne` 的**第一道门**，放在 `now > entry.expiresAt` 自清（`:3086-3089`）**之前**，也要放在 `watcher === undefined` 早退（`:3090-3094`）**之前**。后者容易被漏掉：重启后协调者会话还没打开时 watcher 就是 undefined——按 FR-10 自己的哲学「现任不 live 也照写」（`:2600`），续期门是**名册真值**，不该看进程内活性。放错位置 = 协调者 12 小时没开机，注册照样死。
- **rearm / stopTimer**：续期只改 `expiresAt`，不动 `intervalMinutes`，所以**不需要 reschedule**（`schedule` 的闭包只捕获 id，`:2937`；`patrol` 每轮从 `policy.get()` 现读条目，`:3127`，无陈旧引用问题）。健康条目从此到不了 `removeWatchdog`，`:3196` 那条「全过期才挂清扫定时器」的路径只是更少触发。
- **并发**：`policy.update` 是整数组换写、后写胜。两个巡逻交错时可能互相丢一次续期——但窗口还开着，下一轮（≤10min）自然重试，自愈。这与现有 `removeWatchdog`（`:2950-2953`）的风险类别相同，不引入新类别，值得一条测试钉住。
- **失败方向**：续期写失败（settings 服务抖动）⇒ 条目保留旧 `expiresAt` ⇒ 退化为今天的行为（到期自清）。fail 方向朝着现状，安全。

## ② 会不会与既有到期清扫 / rearm / stopTimer 打架？

**有一个真实的坑，但可以消掉；其余不打架。** 逐项：

1. **顺序坑（致命）**：`patrolOne` 的第一道门就是 `now > entry.expiresAt → removeWatchdog`（`:3086-3089`，audit D1「TTL 自清最先」）。续期判定必须**放在这道门之前**，否则到期即删、永远续不上。这是「甲」能不能成立的第一细节。

2. **清扫链停摆坑（真实、必须修）**：`rearm()` 对过期行不挂定时器、只给**最新那条过期行**挂一个清扫专用定时器（`:3181-3196`），清扫靠 `removeWatchdog` 末尾的 `rearm()` 接棒（`:2957-2963`）。一旦续期让某条行**不再走删除**，而队里还有「该合法死掉」的过期行（比如协调者已换的旧行），这些行就**永远没人碰**——链断了。⇒ **续期写盘后必须补一次 `rearm()`**：它把续出来的行排上自己的定时器（`schedule` 先 `stopTimer` 同 id，`:2935`——所以连「清扫定时器指向它」的情况也被干净接管，不会双定时器），同时给其余过期行重新接上清扫链。幂等、5 行成本，这是甲与既有机制共存的**必要粘合剂**。

3. **不打架的部分**：`stopTimer`/`schedule` 幂等；续期不改 id ⇒ `ticked`/`lastAgentState`/`digested` 键全部保留，摘要去抖状态不丢；`policy.update` **不会**重触发 attach 后置链（`:1941-1952` 只写 scope，`notifyAttached` 只在挂载时发，`:1929-1937`）⇒ 无递归。并发写是既有特性（13 条定时器本就可同时写），续期写丢了下个 tick（10min 内、行仍未续）自愈，无需新增锁。

4. **一个陷阱（做方案时要绕开）**：不要把续期做成 `patrol()` 外层循环里的「预扫全表」——循环迭代的是 `policy.get().watchdogs` 的**快照**，续期后再碰到旧 entry 对象会拿旧 `expiresAt` 走删除门，把刚续的行删掉。放在 `patrolOne` 里、对**本条目**判定并 `return`，天然无此问题（生产上每个定时器都是 `patrol({id})`，只巡逻自己那条）。

## ③ 续期窗口与边界

**关键洞察：有「复活分支」之后，窗口参数可以直接消灭。**

- **续期判定 = `origin === "auto" && now >= entry.expiresAt`**（到期即续）。窗口 0 有两个意外的好处：
  - 消除了「定时器相位 vs 到期时刻」的赛跑——实盘读数里 00:14 rearm、00:27:54 到期，若窗口<20min 且相位不巧，第一 tick 可能落在到期**后**，窗口方案就漏了。到期即续则永远命中（到期后的 tick 照样续）。
  - 少一个魔法常量，少一道「提前多久」的评审争论。
- **续期长度**：`now + WATCHDOG_DEFAULT_TTL_HOURS * 3600000`（+12h，`:278` 同一常量）。TTL 从「租约」降级为「反失控保险丝」：插件巡逻死了、行到期就自然清掉——这正是 TTL 该干的事。
- **续期不碰 `createdAt`**：注意 `planAutoWatchdog` 既有刷新分支会把 `createdAt` 重写成 now（`:2574`）。续期是新语义（租约顺延，不是重建），应保留原 `createdAt`，只加一个 **`renewedAt: now`** 字段。
- **留痕：必须，且不能走 logger**。本部署 `ctx.logger?.warn` 是空操作（FR-17 的存在理由就是「后置链发生了什么完全不可见」，`:13656-13658`）。⇒ 落**行字段** `renewedAt`，并在 `watchdogLines`（`:4551`，状态卡 §③ 与 `team_link_watch list` 共用）渲染「上次续期 …」。写一次看得到一次，零新增读面。

```js
        await policy.update({ watchdogs: policy.get().watchdogs.map((w) => w.id === entry.id ? next : w) }); // 与 :2716-2719 同一落点、同一写法
    } catch { return false; }                                              // fail-open：下个 tick（仍到期且有效）重试
    rearm();                                                               // ★ 问②：续出的行挂定时器 + 其余过期行的清扫链不断
    return true;
}
```

**为什么这是最小正确切法**：复用 `planAutoWatchdog`（它已经会刷新 targets、保持 id、顺延 expiresAt，`:2571-2575`——顺带把「targets 建队后冻结」的隐性缺口每 12h 刷新一次）；`policy.update` 单落点；`rearm()` 一个调用同时解决挂表与清扫链。**不建**新的周期任务、**不动** ensure、**不改** armTeamWatchdog、**不加**窗口常量。

**被否决的更小方案**：2 行盲改 `expiresAt`（见问⑤，掩盖合法失效，不可接受）；事件驱动 GC——在 set-role/retire/rotation 落定时删旧行、TTL 拉满（否决理由：用户在**设置 UI 直接改 teams** 不经任何工具代码，事件钩子永远漏这一类变更；读时门禁对任何改法一视同仁）。

## ⑤ 会不会掩盖「注册本身该失效」的合理语义？

**盲续会，门禁版本不会。** 我先核实了：auto 行今天**唯一**的 GC 就是 TTL 到期（`removeWatchdog` 的调用点只有 `patrolOne` 到期门一处；set-role `:5772`、retire `:5808`、rotation claim 落定都**不**清理 watchdogs；`clear` 又拒清 auto，`:13091-13094`）。所以「到期」现在**身兼两职**：用户可感知的租约 + 换人/删队的隐形 GC。续期必须把这两职拆开：

| 失效场景 | 门禁判定 | 结果 |
|---|---|---|
| 团队从名册删除（含设置 UI 直改） | `team === undefined` | ❌ 不续 → 到期即删（原语义保留） |
| 协调者换人（set-role / rotate 落定） | `watcher !== 现任` | ❌ 不续 → 删除；新协调者的行由下次 attach/arm-team 建 |
| 协调者退役（空缺） | `current` 非本行 watcher | ❌ 不续 → 删除 |
| 队缩到除协调者外无人 | `planAutoWatchdog` 返回 error | ❌ 不续 → 删除（与建队时拒绝同一语义） |
| manual 行 | `origin !== auto` | ❌ 根本不进续期分支，用户自选 TTL 逐字节不变（audit D1 对 manual 原样成立） |

**两个需要你（父侧）在设计档里明确拍板的语义决策**：

1. **观察者会话已关/不 live 时不拦续期**（我建议：以名册为准，不查活性）。理由：工作台摘要挂在**团队**上，不是挂在那个会话窗口上；`patrolOne` 的 watcher-dead 门（`:3090-3095`）本来就压住了对死观察者的全部输出，留着行零噪音零成本，协调者会话重开（长开机、不重启）时摘要**自动恢复**——正好是原始投诉的另一半。代价是 A4「保留至 TTL」的措辞从「12h 上限」改成「名册有效期内长存」，需在文档里如实改口径。保守替代（要求 watcher live 才续）会重新引入「协调者窗口关着、机器长开 ⇒ 摘要静默熄灭」，我否决。
2. **一个修法盖不住的既有洞（建议写进「非目标」）**：换届后**新**协调者的行要等下次 attach/重启才建（ensure 不周期跑）。这与 12h 洞同形但独立存在。若想一并关掉，是「甲+」=巡逻里加节流版周期 ensure——改动面大得多，本批不建议；本批只修「已存在行的续命」。

## 先说三句话

1. **甲是对的方向**，但裸甲有一个语义陷阱（⑤）和一个覆盖盲区（④），都得在设计上堵掉。

## ① 甲 vs 乙：甲是治本，乙单独是半修

`ensureTeamAutoWatchdogs` 全仓只有两个调用点：attach 后置链（`lib/index.js:13670`）和 `arm-team`（`:13156`）。两个都是「挂载时刻」事件，**长开机进程里永远不会再被触发**。所以乙（把 `:2614-2617` 的 `continue` 改成照调 `armTeamWatchdog`）只在重启/手动补挂时续期——用户投诉的场景（连续开机 12h+）下它一次都不会跑。**甲必须做，乙单独不够。**

甲的优势是搭便车：每条注册本来就有自己的 10 分钟巡逻定时器（`:292` `WATCHDOG_AUTO_INTERVAL_MINUTES = 10`，`:2936` 的 `setInterval`），它是进程里**唯一**已经周期性触碰每条活注册的机制。续期挂在它身上，零新增定时器、零新增生命周期。

## ② 与到期清扫 / rearm / stopTimer 的关系：不打架，但有两条排序铁律

逐一对账：

- **stopTimer**：续期**不需要**调 `schedule`（巡检间隔没变），只写 `policy.update`。定时器回调是 `patrol({ id })`，每轮现读 `policy.get().watchdogs`（`:3127`）——新 `expiresAt` 下一轮自动被读到。⇒ 与 `stopTimer`/`cancel`/dispose **零交互**。
- **rearm（`:3175-3200`）**：续期不增删 id，rearm 的计数、跳过过期条目（`:3184`）、兜底清扫定时器（`:3196`）语义全部不变。`removeWatchdog` 尾部的接棒 rearm（`:2963`，t-14 A）也不受影响。
- **到期清扫（`:3086-3089`）**：这是唯一需要排序纪律的地方。铁律两条：
  1. **续期判断必须在 `now > entry.expiresAt` 这道门之前**——否则过期发生在两个 tick 之间的条目会先被 `removeWatchdog` 收掉，续期永远没机会。窗口 > 巡检间隔时，活条目必然在「未过期但已进入窗口」的 tick 上遇到续期判断，与到期门**永不竞争**（两者按同一时钟谓词划界：门管 `now > expiresAt`，续期管 `now <= expiresAt && expiresAt - now <= WINDOW`）。
  2. **绝不复活已过期行**。`now > expiresAt` 的条目照旧走 `removeWatchdog`。这样评审裁定 #9（`:3181-3184`）与 audit D1 的「TTL 自清【最先】」语义**逐字不动**——过期即死，续期只发生在活着的条目上。
- **重入**：同一条目的自有定时器与一次全量 patrol 重叠时可能双双续期——policy.update 是既有唯一写口，两次写各算各的 `now + 12h`，最后写赢，无害。
- **只读纪律**：patrol 在生产里只有定时器一个调用点（`:2937`；状态卡等只读路径不触发它），所以续期写不会污染 W5/W9 的「读路径零写入」断言（`host-half.test.mjs:9369`）。

## ③ 窗口与边界

| 决策点 | 建议 | 理由 |

| 提前多久续 | **30 分钟**（新常量，如 `WATCHDOG_AUTO_RENEW_WINDOW_MS`） | 硬约束是 > 巡检间隔 10min，否则过期可能落在两个 tick 之间；30min = 3 次 tick 机会，容忍两次续期写失败 |

## ④ 更小且更正确的切法：甲 + 乙′（一个谓词），不是甲 + 乙

甲按上面的边界实现就是小切（patrolOne 里约 20 行 + 一个常量 + 一个字段）。**但核代码时发现一个甲盖不住的同源洞，必须同批修**：

**冷启动超 12h 的洞**：机器关机超过 12h 后开机 ⇒ 所有 auto 注册在 attach 时已过期 ⇒ `ensureTeamAutoWatchdogs` 的 `existing` 查找**不查 expiresAt**（`:2612-2613`），把过期行当「在场」报 `present` 然后 `continue`（`:2614-2617`）⇒ rearm 只给最新那条过期行挂清扫定时器（`:3196`）⇒ 清扫链把它们**逐条收掉**（t-14 A 机制，`:10508-10523` 有测试钉着）⇒ **工作台摘要当场死透，且这次连「等 12 小时」都没有，是几分钟内消失**，直到下次重启或手动 arm-team。用户原始投诉在这个时序下**照样复现**，裸甲完全救不了（过期行没有巡逻定时器，续期判断根本遇不到它）。

修法（乙′，一个谓词）：`:2612` 的 `existing` 查找加「未过期」条件（`&& existing.expiresAt > Date.now()`）。过期行随即落到 `armTeamWatchdog` ⇒ `planAutoWatchdog` 的 `:2573-2575` 分支命中（它自己不查过期）⇒ **同 id 原地刷新** expiresAt/targets ⇒ `:2724` 挂上定时器。**那条写了却永远跑不到的续期分支，正是为这个场景铸的**——乙′只是把它接上线。

原方案乙（在场也无条件 refresh）**不必做**：attach 时活条目距到期最远不过窗口外，巡逻会接手，多一次写没有收益。

合并后仍是一个小批次：甲 ~20 行 + 乙′ 1 行 + 常量与字段 + 锚测试。

## ⑤ 会不会掩盖「该失效」的合理语义：裸甲会，加两道门就不会

TTL 的设计意图在代码与测试里写得很清楚：

- **死观察者边界**：`markWatcherDead` 注释「keeping the registration until its TTL」（`:2995-2998`），测试钉着「观察者死了注册留到 TTL」（`host-half.test.mjs:2083`）；
- **生命周期声明**：clear 拒绝文案「它随团队存在，只能靠 TTL 到期或团队解散消失」（`:13094`，U17 `:10820` 钉着）。

注意第二句的**意图**是「随团队存在」——12 小时把**活团队**的工作台静默掐死恰恰是对该语义的违背，不是该语义本身。但裸甲（见条目就续）会把三个合理的死法也续没。解法是给续期加**两道门**（正好 `patrolOne` 里已有现成的观察者读取点）：

1. **观察者活着**：续期判断放在 `:3090-3095` 的观察者活性检查**之后**——观察者不在 ⇒ `markWatcherDead` + return ⇒ 不续 ⇒ 照旧死于 TTL（`:2998` 语义逐字保留）。观察者回来时（`:2088` 的既有恢复行为）若已进入窗口，自然被续上，自洽。
2. **还是现任协调者**：`roleOf(team, COORDINATOR_ROLE)?.current === entry.watcherSession`（`:2607` 同款读法，纯内存读）。团队已退役（名册查不到）或协调者已换人 ⇒ 不续 ⇒ 死于 TTL。

两道门之后，「该死」的三条路（观察者死 / 换人 / 团队退役）全部照死不误，「不该死」的唯一情形（活观察者 + 在职 + 团队在场）被续上——与「随团队存在」的文档语义对齐。

**要点名的一个残留缺口（建议列为本批非目标）**：协调者**中途**换人时，新现任在下次 attach/arm-team 之前不会有自己的 auto 注册（ensure 不周期跑）。这是**既有**缺口，甲不制造也不修它；想修得另起「名册变化钩子」的设计，别塞进本批。

| **★ 续期写盘后必须补一次 `rearm()`** | ✅ **采纳**（**仅 deepseek-v4-pro 独有**） | 复核成立且**是本批最容易被漏的细节**：`rearm()`（`:3181-3196`）对过期行不挂定时器、只给最新那条过期行挂清扫专用定时器，清扫链靠 `removeWatchdog` 末尾的 `rearm()`（`:2957-2963`）接棒。续期让某条行不再走删除 ⇒ 同队里「该合法死掉」的过期行**永远没人碰**，链断。⇒ 续期后补 `rearm()`：既把续出的行排上自己的定时器（`schedule` 先 `stopTimer` 同 id，`:2935`，不产生双定时器），又给其余过期行重新接上清扫链。 |
| **不要把续期做成 `patrol()` 外层「预扫全表」** | ✅ **采纳**（deepseek 独有的陷阱） | 外层循环迭代的是 `policy.get().watchdogs` 的**快照**；续期后再碰到旧 entry 对象会拿旧 `expiresAt` 走删除门，把刚续的行删掉。⇒ 只在 `patrolOne` 内对**本条目**判定。 |
| **切到 agent-team 档的团队要不要同时设门** | ✅ **采纳「不设门」** | 与现状同级（今天 ensure 照样为 agent-team 档铸注册）⇒ 设门属**扩面**。列入本批**非目标**，避免两条路径语义分叉的半成品。 |
| **续期顺带重算 `targets`** | ✅ **采纳** | 走 `planAutoWatchdog` 的 refresh 分支（`:2573-2575`）天然重算 ⇒ 顺带修掉「成员中途入队但从未被盯上」这个**同源缺口**。 |
| **`renewedAt` 加性字段 + 保留原 `createdAt`** | ✅ **采纳**（三份一致方向） | `planAutoWatchdog` 既有 refresh 分支会把 `createdAt` 重写成 now（`:2574`）—— 续期是新语义（租约顺延，不是重建）⇒ 落码时显式保留原 `createdAt`。 |
| **留痕必须落**行字段**而非 logger** | ✅ **采纳**（deepseek） | 本部署 `ctx.logger?.warn` 是空操作（FR-17 的存在理由就是这个），⇒ 只写 logger 等于没留痕。 |
| **`renewedAt` 会被读面归一化白名单静默丢掉** | ✅ **采纳**（glm-5.3 独有的坑） | `watchdogList` 的归一化（`:1228-1251`）是**固定键白名单**，不加一行归一化，字段每次读写循环都被丢掉。⇒ 落码必须同批改归一化。 |
| **FR-R2（周期调用 ensure 复活）** | ✅ **采纳**（glm-5.3） | 与 kimi 的「乙′」**合为两条 FR**（治不同时刻，见 §3 的分歧 4）。 |
| **乙′（`ensure` 的 `existing` 查找加「未过期」谓词）** | ✅ **采纳**（kimi-k3 独有） | 复核成立：`:2612-2613` 的 find **不查 `expiresAt`** ⇒ 冷启动（关机 >12h）后过期行被当「在场」报 `present` 然后 `continue`，随后被清扫链逐条收掉 ⇒ **工作台当场死透**（比 12h 慢死更快）。这是与 R1 同源但**独立存在**的洞。 |
| **「摘要投递时顺带滑动 TTL」** | ✅ **采纳否决**（glm 给出） | 摘要有签名去抖、安静团队 12h 一条都不发 ⇒ 安静团队照样死，恰好放过最需要兜底的场景。 |
| **事件驱动 GC（在 set-role/retire/rotation 落定时删旧行）** | ✅ **采纳否决**（deepseek 给出） | 用户在**设置 UI 直接改 teams** 不经任何工具代码 ⇒ 事件钩子永远漏这一类变更；读时门禁对任何改法一视同仁。 |

### 2.2 最终采纳的方案（本批实施的规格）

**三件套**（详见设计档 `docs/2026-10-12-watchdog-renewal-design.md`）：

- **FR-R1（续期，核心）**：`patrolOne` 内、**到期门之前**、窗口内、**名册门**通过 ⇒ 调 `planAutoWatchdog` 的 refresh 分支（保留 `id` / `createdAt`，写 `expiresAt = now + 12h` 与 `renewedAt = now`）⇒ 单笔 `policy.update` ⇒ **`rearm()`**。
- **FR-R2（乙′，冷启动洞）**：`ensureTeamAutoWatchdogs` 的 `existing` 查找加「未过期」谓词 ⇒ 过期行落到 `armTeamWatchdog` ⇒ 命中那条**写了却永远跑不到**的 refresh 分支 ⇒ 同 id 原地刷新。
- **FR-R3（运行期复活）**：巡逻内**去抖地**周期调用现有 `ensureTeamAutoWatchdogs`（语义逐字不变），治「机器睡过窗口 + 到期点」——那条路径今天没有任何东西会重建它。

**参数**：窗口 **2 小时**（见 §3 分歧 2）；续期长度复用 `WATCHDOG_DEFAULT_TTL_HOURS`（`+12h`），不另造时长；失败方向 fail-open（写失败 ⇒ 保留旧 `expiresAt`，退化到今天的行为）。

## §4 教训（**主代理写**）

1. **会诊的价值是并集，不是多数票。** 三份意见在**方向**上完全一致，但各自的**独有发现**才是本批的关键：glm 发现「`targets` 建队后冻结」与「归一化白名单会静默丢掉新字段」；deepseek 发现「续期后清扫链停摆」与「外层预扫的快照陷阱」；kimi 发现「冷启动 >12h 的洞」。**任何单独一份都不足以写对设计**——如果只取一份，设计会带三个洞上线。
2. **我给 brief 时漏了「不变式」。** 我原案的「甲」是**裸甲**；三份意见**一致**指出裸甲会把「团队已删 / 协调者已换 / 已退役」这些本靠 TTL 兜底的 GC 续成永生僵尸。根因是我在 brief 里只写了「怎么修」，**没写「什么是合法失效」**。⇒ 下次提 brief，要把**不变式与失效条件**一并写进去。
3. **方案的前提要靠代码事实检验，不能靠推理的美感。** deepseek 的「窗口 = 0（到期即续）」在推理上更优雅（少一个常量、消除相位赛跑），但它依赖「过期行仍有巡逻定时器」——而 `rearm()` 的代码事实是**不给过期行挂表** ⇒ 前提不成立。**同样的道理：本次三条意见里凡我采纳的，都逐条回到了源码行核对。**
4. **「三份都没提」不等于「没问题」。** deepseek 的 `rearm()` 发现是三份里**唯一**一份，另外两份还明确主张了相反的做法（「不碰定时器」）⇒ **独立意见之间的一致意见也可能是共同盲区**，采纳前必须自己回到代码。本次即如此。
